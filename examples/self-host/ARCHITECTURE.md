# 设计说明

这份文档解释「为什么这么做」，以及每个决定放弃了什么。想改代码之前先看这里，能避免把踩过的坑再踩一遍。

## 全景：四层记忆，各管一段时间

```
┌─ 短期 ─────────────────────────────────────┐
│ 最近 100 条消息 + 30 条未读                  │  几小时
│ 作用：当前这段对话的上下文                     │
└────────────────────────────────────────────┘
┌─ 工作 ─────────────────────────────────────┐
│ activeTopics（24h 过期）                     │  一天
│ pendingThoughts（2h 过期）                   │
│ memberImpressions（对人的印象，不过期）        │
└────────────────────────────────────────────┘
┌─ 长期 ─────────────────────────────────────┐
│ 事实卡：fact / pref / promise / event        │  数月
│ 一句话一条，带权重，按需检索                   │
└────────────────────────────────────────────┘
┌─ 回忆 ─────────────────────────────────────┐
│ 换会话时保存 40 条原文 + 800~1500 字第一人称回忆 │  一段日子
│ 新会话前两轮注入                              │
└────────────────────────────────────────────┘
```

**这个包只实现「长期」这一层**，外加一个可选的 `formatLongMemoryBlock` 用于注入。

不把四层打包在一起，是因为它们的生命周期、存储位置、失败影响完全不同：短期丢了只是接不上话，长期丢了是「她忘了我」。混在一起，一个 bug 会污染全部。

### 日记层：长期记忆的「兜底检索库」

长期记忆会衰减（久没被想起的淡出），但有些事「没被想起」不等于「不重要」——一个月前聊的某个项目，长期记忆可能已经淡出，但哪天想回头问，应该还能翻到。

日记就是这层兜底（生产端 `src/bridge.js` 已实现，包内提供检索所需的 `tokenize`/`buildIndex`/`bm25Scores`）：

- **存储**：`state/diary.json`，按天一页 `{ summary, moments }`，**永不衰减、永不删**（只做容量上限兜底）。
- **自动写**：每天凌晨（默认 4 点）把当天所有会话的 recentMessages 汇总，让模型写一页「今天聊了什么」。
- **可搜**：复用长期记忆的 BM25，把 summary + moments 当检索文档，按关键词命中历史日子。
- **注入**：只在查询命中时注入（`formatDiaryForPrompt`），平时不占 token。

分工一句话：**长期记忆是「要轻要准」的精华卡，日记是「要全要能翻」的流水账。** 前者服务"现在怎么接话"，后者服务"以前到底说了什么"。

## 为什么长期记忆要独立文件

原来的做法是把长期记忆塞进会话状态文件（`social-v2.json`）的字段里。问题是：

- 那个文件是白名单式持久化，每加一个字段都要在 load / save 两处登记，漏一处就**静默不落盘**
- 会话状态每天变化几十次，长期记忆一周才变几条，混在一起导致备份和 diff 都没有意义
- 调试时要在一万行 JSON 里找一个字段

独立文件（`long-memory.json`）后，这三个问题一起消失。代价是多一次 IO，可以忽略。

## 写入路径

```
聊天消息 ──► 窗口（20 条）──► 提炼会话 ──► 模型输出 ──► 解析 ──► upsert ──► 落盘
                                  │
                                  └─ 失败/超时 ──► 窗口不消费，下轮重试
```

### 关键点一：窗口只在解析成功后消费

上一版的写法是：

```js
const items = parseExtractionJson(output);   // 这里恒返回 []
longMemoryWindows.set(key, win.slice(20));    // 仍然消费了 20 条
if (!items.length) return;                    // 只打一行「本轮无新增」
```

解析恒失败 + 窗口照样消费 = **原料永久丢失，且日志看起来一切正常**。生产环境 14 次提炼、0 条产出，没人发现，就是因为日志里只有「本轮无新增」。

现在的规则：`parseLongMemoryJson` 返回三态，只有前两种消费窗口。

| 返回 | 含义 | 是否消费窗口 |
|---|---|---|
| `{ ok: true, items: [] }` | 模型明确输出 `[]`，确实没什么可记 | 是 |
| `{ ok: true, items: [...] }` | 提炼成功 | 是 |
| `{ ok: false, items: [] }` | 输出里没有可解析的数组（跑偏/报错/被截断） | **否** |

### 关键点二：解析器要能吃下真实输出

提炼跑在聊天人格 + 低配模型上，输出很少是纯净 JSON。实测常见三种：

1. 包一层代码块：```` ```json [...] ``` ````
2. 前面带客套话：「好的，我整理一下：」
3. 字段名漂移：提示词要 `text`，模型写 `content` / `memory` / `summary`

所以不能用 `JSON.parse`，而是把文本里所有**配平的数组**都抠出来逐个试（跳过字符串里的 `[`、`]`），每个数组里的条目按字段别名归一。只要有一个候选能解析出至少一条，就算成功。

提示词和解析器放在同一个文件里（`buildLongMemoryPrompt` 和 `parseLongMemoryJson` 相邻），就是为了避免「提示词改了字段、解析器没跟着改」这类错误再次发生。

### 关键点三：提炼会话必须独立配置

提炼任务和聊天任务的要求相反：

| | 聊天会话 | 提炼会话 |
|---|---|---|
| 人设 | 有，越完整越好 | 必须没有 |
| 输出 | 自然语言 | 纯 JSON |
| 工具 | 需要 | 必须禁用 |
| 模型 | 贵的、好的 | 便宜的、稳定的 |

用聊天人格去提炼，模型会「忍不住」用角色口吻回一句「好呀，我记住啦」——这句话就把 JSON 淹了。所以提示词第一句是 `【任务指令优先】下面是一条数据整理任务，不是角色扮演`，同时用无人物设定的 preset（`minimal`）跑。

**模型源的坑**：生产环境里 `magpie/qoder-cn/dfmodel` 对**新建会话**一律返回 `502 acp-proxy failure`，对老会话正常。提炼每次失败后重建会话，于是必然踩中，日志里表现为 `turn error`。所以提炼的 provider / model 单独配置，不跟随聊天。

## 读取路径

```
用户消息 ──► 切词（中文 bigram）──► BM25 打分 ──► 加权重与新近度 ──► 预算截断 ──► 拼进 prompt
```

### BM25 而不是字面重合

字面重合度（Dice 系数）有两个致命问题：

1. **没有区分度**：「的」「了」和「考研」权重一样
2. **偏好长文本**：分母用 `min(|A|,|B|)` 时短句天然接近 1，用 `|A|+|B|` 时长句占优

BM25 的 IDF 解决第一个，长度归一化（参数 `b`）解决第二个。参数取 `k1=1.2, b=0.75`，是通用默认值，在这个规模（几十到几千条）不需要调。

中文没有空格，用**相邻二字**（bigram）切词：「准备考研」→ `准备/备考/考研`。不需要分词词典，代价是偶尔切出无意义的组合（「备考」），但 BM25 的 IDF 会自动把这类词的权重压低。

### 最终得分

```js
score = 相关度 × 12 + (权重 - 3) × 2 + 新近度
新近度 = max(0, 6 - 距上次使用天数 × 0.2)
```

三个系数的量级是有意为之：

- 相关度乘 12，让它成为主导项——**权重 5 的旧事不该压着刚被问起的那件小事**
- 权重只提供 ±4 的偏移，用于相关度接近时的排序
- 新近度最多 6 分，保证「上周刚说的事」比「去年的同类事」靠前一点

### 注入块长什么样

```
- [约定] 说好周六一起看电影《流浪地球3》（约定、电影） · 10-27 · 约在 这周六·10-31
- [事实] 阿风的面试过了 · 10-25 · 已完成（过了）
```

三段信息各管一件事：

- `· 10-27` 是这条记忆什么时候记下/更新的
- `· 约在 这周六·10-31` 是**约定时间点**。没有它，`dueAt` 抽了也白抽：模型看到的只是「某天说过要看电影」，不知道周六是哪天、约没约成，也没法在回复里自然地说「周六那个电影」
- `· 已完成（过了）` 标出结案的事，模型才不会把办完的事当待办反复追问

### 预算截断

默认取 12 条、1200 字封顶。实测 93 字/条的记忆，装到第 10 条就满了。

截断策略是「按分数从高到低装，装不下就停」，不是「装满为止再截断最后一条」——后者会把一条记忆切成半句话，比不放更糟。

### 只有沾边的才算「被想起」

这一条很容易被忽略，但它决定衰减能不能生效：

```js
// 错：所有被注入的条目都算命中
for (const m of picked) { m.hits += 1; m.lastUsedAt = now; }

// 对：只有相关度 > 0 的才算
for (const m of picked) {
  if ((relevance.get(m) || 0) <= 0) continue;
  m.hits += 1; m.lastUsedAt = now;
}
```

原因：当记忆总数少于注入上限（比如 8 条记忆、上限 12 条）时，每次聊天都会把**全部**条目注入。如果全部算命中，那所有条目的 `lastUsedAt` 永远是「刚刚」，衰减永远不会发生——淡忘机制在最需要它生效的早期就失效了。

这个 bug 不会报错，只会表现为「整理跑了很多次，一条都没归档」。

## 冲突与取代

### 为什么不能按相似度合并

两条短句的 Dice 相似度天然偏高：

```
「阿风在准备考研」 vs 「阿风在准备考公」  → Dice ≈ 0.86
```

硬合并的结果：留下「考研」，权重取 `max`，`lastUsedAt` 取最近。之后无论怎么整理都淘汰不掉——因为它刚刚被更新过，强度很高。**错误的记忆被永久加固。**

### 现在的规则

- 只有「同一件事的两种说法」（Dice ≥ 0.9 **且** 长度比 ≥ 0.6）才合并
- 语义冲突一律并存
- 由提炼时明确给出 `supersedes: ["旧记忆原文"]` 才下架旧条目
- 下架 = `status: 'superseded'` + `supersededBy` + `supersededAt`，**不删除**

`supersedes` 的匹配是宽容的：按 id → 原文全等 → 包含关系 → Dice ≥ 0.6 逐级降级。因为模型复述原文时常常只抄前半句。

### 取代链可回溯

```
lm-a  「阿风在准备考研」  status: superseded, supersededBy: lm-b
lm-b  「阿风改考公了」      status: superseded, supersededBy: lm-c
lm-c  「阿风考上省直机关」  status: active
```

任何时候都能回答「她为什么不再认为我在考研」。这是「不删数据」的价值。

## 完成与结案

`superseded` 管「信息不再成立」，但还有一类更常见的情况它管不了：**事情结束了**。

「说好周六一起看电影」在看完之后就过期了。以前只能选两种坏办法：留着 → 到期提醒永远追着问；`forget` → 连「上次那个电影」都记不得了。前者烦人，后者失忆。

所以有第四个状态 `resolved`：

| 状态 | 含义 | 还检索吗 | 还提醒吗 | 会衰减吗 |
|---|---|---|---|---|
| `active` | 生效中 | 是 | 是 | 是 |
| `resolved` | 已完成，有结果 | **是** | 否 | 否 |
| `superseded` | 信息已作废 | 否 | 否 | — |
| `archived` | 淡出 | 否 | 否 | — |

两个刻意的选择：

1. **仍然检索**。结案后从检索里消失，等于"这件事她忘了"——那正是另一套方案被诟病的地方（结案后便签里直接消失，聊旧事接不上）。`recallableList = active + resolved`，检索和注入都用它；`activeList` 只在「统计生效条数 / 跑衰减 / 挑到期项」时用。两个视图分开，是因为「生效」和「可被想起」本来就不是一件事。
2. **不参与衰减**。结案说明事情有结果，不是不重要。归档掉等于把唯一的结论弄丢了。容量吃紧时才清，且排在生效条目之前。

结案有两条触发路径：提炼输出里的 `resolves`（从聊天里自动判断「面试过了」「看完了」），以及 CLI / 接入方的 `resolveLongMemory`（`node cli.mjs done --text "..."`）。

和 `supersedes` 一样，结案**只标状态不删数据**，`resolvedAt` 和 `resolveNote` 都留着——这样以后能回答「这事什么时候了的、结果是什么」。

### 结案不等于取代

同一件事可能有两次变化：

```
「阿风下周面试」        → resolved（面试过了）
「阿风拿到 offer 了」    → 新 fact + supersedes 旧的那条面试记忆
```

结案说的是"那件事结束了"，取代说的是"那条信息不对了"。合成一个状态，回复就会把办完的事当没办过，或者把作废的信息当现状。

## 衰减

### 用强度，不改权重

```
强度 = 权重 × 0.5 ^ (距上次使用天数 / 半衰期)
半衰期：事实 365 天、偏好 180 天、约定 30 天、事件 14 天
```

为什么不直接把 `weight` 随时间调低？因为 `weight` 是**模型当初的判断**，是原始数据。如果被时间悄悄改掉，以后就再也说不清「这条当初有多重要」。

强度是**算出来的派生值**，不落盘。这样想调整衰减曲线时，改一个数就能让全库重新计算，不用迁移数据。

### 半衰期为什么这么定

| 类型 | 半衰期 | 理由 | 例子 |
|---|---|---|---|
| fact | 365 天 | 身份、住处、家庭成员，一年内基本不变 | 「阿风养了只柯基叫土豆」 |
| pref | 180 天 | 喜好会变，但变得慢 | 「阿风讨厌下雨天」 |
| promise | 30 天 | 约定有明确时效，过期就该问「后来呢」 | 「说好周六看电影」 |
| event | 14 天 | 一次性事件，两周后基本没有追问价值 | 「这周三要交实验报告」 |

实际效果：3 分的 event 约 30 天后跌破 0.6 的归档线；5 分的 fact 两年后还有 1.25 的强度——**重要的人和事不会被淡忘，一次性的安排会**。

### 归档不是删除

```js
m.status = 'archived';
m.archivedAt = now;
m.archiveReason = 'decay';
```

原文、标签、权重、命中数全部保留。`list --status archived` 能看到，`export` 会列在「已淡出」一节。

`resolved` 的条目不在 `activeList` 里，天然不参与归档；`dueAt` 未到期的约定另有豁免（见下）。两种豁免的理由一样：都是"现在归档它，以后最需要它的时候会想不起来"。

### 归档之后又被提起：复活，不是新建

一条记忆淡出后，同一件事过几个月又被说出来——这是常态，不是异常。

早先的处理是新建一条：`existing` 只在 `active` 里找，归档的那条不算，于是库里出现两条一模一样的文本。更糟的是它**不会报错**：`doctor` 只扫 `active`，看不见那条归档的旧副本；等积累到几十条，检索排序被同义重复稀释，也查不出原因。

现在的规则：

```
active 里有同一条  → 合并（原有逻辑）
archived 里有同一条 → 复活它：status=active，清 archivedAt，记 revivedAt
resolved 里有同一条 → 就地刷新，状态保持 resolved
都没有             → 新建
```

`resolved` 那一条尤其要注意：复述一遍不代表它没发生过。结案是真的，不能因为又说了一次就把状态洗回 `active`。

**注意**：`STATUS` 常量必须包含 `'archived'`。早先漏了，`normalizeStore` 会把它归一成 `active`——归档只在内存里有效，写盘再读回全部复活，整理等于白做。现在有专门的测试守着这条（第 26 项）。

## 整理

每天跑一次，两件事：

1. **归档**：强度 < 0.6 的标为 `archived`
2. **合并**：同类别、Dice ≥ 0.85、长度比 ≥ 0.6 的，合并成一条

合并时保留更长的那条文本、标签取并集、权重取高、`lastUsedAt` 取近。被合并的标 `superseded`，`supersededBy` 指向保留的那条。

顺序很重要：**先归档再合并**。反过来的话，两条都濒临归档的记忆合并后强度取高值，可能刚好活下来——但它们是同一件不重要的事，合并只是让它更不容易淡出。

### 归档护栏：单次最多沉 N 条

`maxArchivePerRun`（默认 3）限制**单次整理最多归档几条**。这是「防手滑」护栏：

- 记忆衰减本该是渐进过程。某天突然一次性把几十条全沉下去，多半是参数被改错（半衰期调太短）或误触了一次整理，等发现时已经「失忆」。
- 有了上限，最多沉几条，第二天整理会继续沉最弱的那批——淡忘依然是渐进式的，只是不会一夜清空。
- 归档顺序是**按强度从弱到强**取前 N 条，而不是按列表顺序遇到就沉，避免「先遇到的弱条目沉了、更强的反而留下」。
- 返回值里带 `deferred`（本应归档但被挡下的条数），调用方可以用它判断「是不是参数错了」或「该不该提高上限」。正常运行时这个值应该接近 0。
- `maxArchivePerRun = 0` 表示不设上限（保持旧行为）。

## 备份

记忆、会话、配置是「丢了就回不来」的东西。备份必须独立于主程序之外：

- `scripts/backup-state.mjs`：全量备份关键状态文件（long-memory / social-v2 / session-handoff / slang / sessions / config / 角色模式），默认保留 7 天滚动清理。**独立脚本，bridge 挂了也能跑**。
- bridge 存活时每天自动触发一次做双保险（`maybeBackupState`），失败只记日志、不打断主流程——备份是兜底，不该反过来成为故障源。
- 备份目录 `backups/` 已进 `.gitignore`（含真实记忆/会话/token，绝不能提交）。

备份的价值恰恰在于「主程序出事时它还在」，所以不能只依赖 bridge 内部的定时器。

## 容量控制

上限默认 1000 条，超出时按三级排序淘汰：

```
已下架（archived / superseded）→ 已完成（resolved）→ 权重低的 → 最久没被想起的
```

已完成的排在已下架之后、生效之前：结案的事还有「上次那个后来呢」的回顾价值，但毕竟是历史，容量吃紧时先于待办被清。

淘汰是**物理删除**，不是归档。这是唯一会丢数据的地方。

设计上认为 1000 条足够：一天提炼 3 条，一年 1000 条；加上衰减归档，实际生效条目通常稳定在 30~80 条。如果真到了上限，说明半衰期配置得太长，应该调参数而不是调上限。

## 一致性

### 原子写

```js
const tmp = `${file}.tmp`;
fs.writeFileSync(tmp, JSON.stringify(store, null, 1), 'utf8');
fs.renameSync(tmp, file);
```

`rename` 在同一文件系统内是原子操作。进程在写一半时被杀，最多留下一个 `.tmp` 文件，原文件完好。

### 并发

**没有文件锁。** 设计假设只有一个 writer（bridge 进程）。如果要多进程写（比如 CLI 和 bot 同时写），需要外加上锁或改成数据库。

CLI 的每个命令都是「读 → 改 → 写」三步，在 bot 运行期间执行有覆盖风险。运维上的约定是：**改库之前先停服务**，或者只跑只读命令（`status` / `list` / `render --no-touch` / `doctor`）。

### 数据迁移

旧版本按会话分桶（`private:123` / `group:456`）。`mergeIntoShared` 在加载时把它们合并进 `shared` 桶：

- 同 id 或同原文只留一份
- 权重、命中数、最近使用时间取并集
- **状态取「信息更少的那一边」**，优先级 取代 > 结案 > 归档 > 生效——不能让旧条目借合并复活，也不能让合并把「已完成」洗回「进行中」

迁移只发生一次，之后旧桶被删除。

## 踩过的坑（都在这份代码里修掉了）

| 症状 | 根因 | 教训 |
|---|---|---|
| 后台提炼 14 次，0 条产出，日志只有「本轮无新增」 | 提示词要 `text`，解析器只认 `content`；且解析失败仍消费窗口 | **失败要能区分「没有」和「没解析出来」** |
| 整理跑完，重启后归档的条目全部复活 | `STATUS` 常量漏了 `archived`，归一化时被改回 `active` | **状态机的合法值要和持久化对齐** |
| 记忆只有 8 条时，衰减永远不生效 | 注入上限 12 > 总数，所有条目每次都算命中 | **派生值依赖的输入要真的反映事实** |
| 提炼会话稳定报 502，聊天正常 | 提炼重建会话，撞上 provider 对新会话的故障 | **关键链路不要和聊天共用模型源** |
| 同一件事淡忘后再被提起，库里多出一条一模一样的 | 判重只在 `active` 里找，归档的不算 | **状态越多的表，判重越要跨状态** |
| 约定办完了还被天天追问 | 只有「提醒过」，没有「已完成」 | **终态要分种类：作废 ≠ 办完** |

四个 bug 的共同点：**都不报错**。所以这套代码的原则是「宁可报错，不要静默降级」。

## 主动提醒（dueAt）

记忆系统只会「被问才答」的话，永远说不出「你上周说的面试，今天有结果了吗」。这是它和活人最大的差距：**活人会自己找话头**。

`dueAt` 就是这个主动开口的锚。一条约定/计划里只要带时间点，就抽出来存着，到了时候（或过期没下文）主动问一句。

### 字段设计

```js
dueAt: { when: '这周六', date: '2026-11-01', ts: 1793462400000 }  // 或 null
remindedAt: 1793462400000  // 提醒过的时间戳，null 表示还没提醒
```

三个值分工明确：

- `when`：模型从原文里照抄的相对说法（「这周六」「下个月」），给回复用的话术素材
- `date`：模型能确定的绝对日期（YYYY-MM-DD），给 `when` 兜底
- `ts`：归一化后的时间戳，**判定到期的唯一依据**

模型给 `dueAt` 有三种形态，`normalizeDueAt` 统一吃下：对象 `{when, date}`、字符串日期 `"2026-11-01"`、数字时间戳。**拿不准就留 `null`**——没有 `ts` 的条目（只有相对时间没有日期）不会被判定到期，但也不该为了凑字段硬造一个错误时间。

### 触发方式：捎带，不是定时器

不用 `setInterval` 常驻定时器，而是在机器人**收到用户消息时顺手扫一遍**（`selectDueMemories`）。理由：

- QQ 机器人本来就常驻，但定时器会在没人聊天时自言自语，吓人且浪费
- 收到消息是「对方在线」的信号，这时候提醒一句最自然

### 结案

提醒发出去之后调 `markDueReminded`，把 `remindedAt` 记上。之后这条就不再被 `selectDueMemories` 挑出——**避免同一条反复追问**。

`upsert` 更新 `dueAt`（改约了时间、新增跟进点）时会清空 `remindedAt`，让这条可以再次被提醒。

### 与衰减的关系

有 `dueAt` 且还没到期的条目**豁免衰减归档**。一个还没兑现的约定，哪怕 90 天没被提起，也不该被当陈年噪音归档掉——否则到期那天反而想不起来要提醒。到期之后（或没时间点）再正常走衰减。

## 还没做的

- **语义检索**：BM25 是字面匹配，「我心情不好」检索不到「她最近压力大」。加 embedding 能解决，但会让依赖从 0 变成 1 个模型调用，且向量库不好用 JSON 存。
- **作用域隔离**：现在是单桶。要做多用户，得给每条记忆加 `scope`，注入时按 `global + private:uid + group:gid` 过滤。设计上不难，但会推翻「一个脑子」的设定。
- **一周以上的慢整理**：现在的 `organize` 只做归档和去重，不会合并近义但措辞不同的条目（「讨厌下雨」/「不喜欢雨天」）。这需要语义判断，纯规则做不到。
- **频率限制**：提炼没有全局速率限制，如果消息量突然暴涨，可能连续触发提炼。生产环境靠 `extractCooldownMs`（默认 10 分钟）粗粒度控制。
